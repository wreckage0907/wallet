## 1. The desk tree view for `Wallet Category` bypasses owner isolation

**Status:** ~~open~~ closed by #11 (6 November 2026) · **Verified:** yes, measured on a live site, before and after

`wallet/permissions.py` warns in its module docstring that `frappe.get_all` and
`frappe.qb` bypass `permission_query_conditions`. That prediction is currently true in
framework code the app does not control.

`frappe.desk.treeview._get_children` (`apps/frappe/frappe/desk/treeview.py`) builds a raw
`frappe.qb` query, filtering only on the parent field, `docstatus < 2` and `disabled`.
There is no permission-query hook and no `has_permission` check. So
`/desk/wallet-category/view/tree` enumerates every user's categories.

### Measurement

Run on `demo.localhost` as a normal (non-Administrator) user:

| Call | 30 Aug 2026 | 6 Nov 2026, framework query | 6 Nov 2026, after the fix |
|---|---|---|---|
| `frappe.client.get_count` on `Wallet Category` | **107** | 107 | 107 |
| `treeview.get_children`, empty parent | **180** root nodes | 690 | **30** |
| Roots not present in the permission-aware list | **150** | 660 | **0** |

The leak grew with the site: 690 roots by November, because every new user's seeded
defaults are roots too. "After the fix" is `frappe.desk.treeview.get_children` resolved
through `override_whitelisted_methods` the way the request handler resolves it.

Expanding a leaked node lists its children too — the same raw query runs at every level.

### Severity is bounded

- `frappe.client.get` on a leaked docname returns **403 PermissionError**. This is name
  enumeration, not a record read.
- `Wallet Category` is the app's only `is_tree` doctype. Accounts and transactions have no
  tree view and are unaffected.
- The PWA is unaffected — it goes through `frappe.client.get_list`, which is
  permission-aware.

The names involved are mostly the shipped defaults, which are identical for everyone. The
exposure that matters is a *custom* category, which can be personal.

### Fix

The fix proposed here originally — a `wallet_category_tree.js` pointing the tree view at
an owner-filtered method — was not enough on its own. It changes what the desk *calls*,
but `frappe.desk.treeview.get_children` stays whitelisted, and so does `get_all_nodes`,
which runs whatever `tree_method` the client names. A direct API call would still leak.

What shipped:

- `wallet/treeview.py:get_children` — the same node shape as the framework's, but through
  `frappe.get_list`, so it carries the ordinary permission query condition (Administrator
  exempt, as everywhere). Any doctype outside `OWNED_DOCTYPES` falls through to the
  framework untouched, so ERPNext trees on the same site are unaffected.
- `override_whitelisted_methods` in `hooks.py` maps the framework method onto it, which
  covers `/api/method/`, `/api/v2/method/` and `get_all_nodes`.
- `wallet_category_tree.js` points the desk tree view at it directly.
- `wallet/tests/test_treeview.py` calls the framework's method name through the override
  resolution, as a second user, and asserts every root and child returned is the
  caller's. Five of its eight tests fail with the override removed.

### Follow-up

~~The `permissions.py` docstring tells reviewers to grep for `get_all`. It should also name
`frappe.qb`, and — the part that actually bit here — framework code that queries on your
behalf.~~ Done: the docstring now names both, and points at `wallet/treeview.py` as the
worked example.

## 2. `Wallet Budget` is referenced but does not exist

**Status:** ~~open~~ closed by #14 (6 November 2026)

`Wallet Budget` appears in `permissions.py:OWNED_DOCTYPES`, and `hooks.py` therefore
registers both `permission_query_conditions` and `has_permission` for it. No such doctype
exists.

Harmless today — the hooks never fire — but it is a dangling promise. Either build the
doctype or drop the two references.

Dropped from both. `test_permissions.py:test_every_isolated_doctype_exists` now asserts
every name in `OWNED_DOCTYPES` is a real DocType, alongside the existing test that the
tuple and both hook maps agree. A budgets feature, if it is ever built, starts from zero
and has to add itself to the tuple — at which point both tests hold it to isolation.

## 3. `requires-python = ">=3.14"` is ahead of the bench

**Status:** ~~open~~ closed by #13 (6 November 2026) — not a bug; the floor is Frappe's

`pyproject.toml` declares `requires-python = ">=3.14"`. The development bench runs Python
3.12.12. A plain `pip install -e .` would refuse to install.

Either loosen the floor to what the app actually needs, or state why 3.14 is required.

### Resolution

The 3.12.12 measured here was the host's Python, not the bench's. The bench virtualenv runs
3.14.3, and it has to: Frappe v16 itself declares `requires-python = ">=3.14,<3.15"`
(checked on the `version-16` branch), so no bench that can run Frappe v16 lacks 3.14.
Loosening the floor would only advertise an install that Frappe refuses one step earlier.

What was actually wrong was the drift around it: `linters.yml` ran 3.13 while `ci.yml` and
`ui-tests.yml` ran 3.14, and the README listed "Python 3.11+" and "Node 18+" as
prerequisites. All three workflows now run 3.14, `pyproject.toml` says why, and the README
lists Python 3.14 and Node 24+ (Frappe v16's `engines`).

## 5. The MCP install is not reproducible

**Status:** ~~open~~ closed by #15 (6 November 2026): the dependency is gone

### Resolution

Frappe ships an MCP server in core from v16.53.0, at `/api/v2/mcp`. Wallet dropped its own
endpoint and `frappe-mcp` with it. There is nothing left to install by hand, the CI step
that did it is deleted, and `pyproject.toml` raises the Frappe floor to 16.53.0 instead.
The old URL, `/api/method/wallet.mcp.handle_mcp`, now answers `410 Gone` with a JSON-RPC
error naming the new one, not a traceback.

Re-measured on demo.localhost (Frappe develop 91cf805, no `frappe_mcp` import anywhere in
the app): `initialize`, `tools/list` and `tools/call` over HTTP as a Wallet user, on both
protocol revisions (`2025-11-25` and `2026-07-28`). `test_gate.py` drives the same
`frappe.mcp.tools` dispatch in CI.

### Original finding

`frappe-mcp` is deliberately not in `pyproject.toml` — it pins `Werkzeug==3.1.3` and
`pydantic~=2.11.7` against Frappe's newer pins, so resolving it would downgrade Werkzeug
and break the bench. It is installed with `--no-deps` instead.

That install lives only in the bench virtualenv. A container rebuild, a fresh `bench init`,
or a Frappe Cloud deploy loses it, and the endpoint fails with
`No module named 'frappe_mcp'`. Nothing in the repo restores it.

The rest of the app is unaffected — nothing else imports `frappe_mcp`.

## 6. `allow_mcp_writes` is site-wide, not per-user

**Status:** ~~open~~ closed by #22 (6 November 2026): per-user opt-in shipped

### Resolution

A write over MCP now needs the site switch **and** the user's own opt-in,
`User.wallet_allow_mcp_writes`, which defaults off and is set from the PWA's *More* screen.
Only that user can change it, and never over MCP. See
[`security-boundaries.md`](security-boundaries.md) for why it is a `User` field and not a
user default.

Re-measured over HTTP as a fresh Wallet user, site switch on: `add_transaction` and
`create_document` were refused until the user opted in. The agent's own attempts to opt in
were all refused (`set_mcp_writes`, `update_document User`, `frappe.client.set_value`).
After opting in from the PWA, both writes succeeded. `test_gate.py` covers each case,
including Administrator being unable to opt a user in.

### Original finding

`Wallet Settings` is a Single, so `allow_mcp_writes` is one switch for the whole site. On a
multi-user site, one System Manager turning it on opens the MCP write path for every
connected agent — each still confined to its own owner's records, but none of them opted
in.

A per-user opt-in would need a field on `User` or a small per-user settings doctype.

## 7. The PWA has no write path

**Status:** ~~open~~ closed for adding, still open for editing

`/wallet/add` records a transaction against any of the user's accounts, through
`wallet.api.transaction_api.create_transaction` — the same function
`wallet.mcp.tools.add_transaction` calls, so the duplicate pre-check and the balance echo
cannot drift between the two front doors.

What remains: **editing and deleting** an existing transaction still means the desk, and
so does creating an account, which is why the Add screen sends a user with no accounts to
`/app/wallet-account/new` rather than growing an account form of its own.
