# Audit — 30 August 2026

First full pass over the app. Findings are ordered most severe first. Nothing here is
fixed yet.

---

## 1. The desk tree view for `Wallet Category` bypasses owner isolation

**Status:** open · **Verified:** yes, measured on a live site

`wallet/permissions.py` warns in its module docstring that `frappe.get_all` and
`frappe.qb` bypass `permission_query_conditions`. That prediction is currently true in
framework code the app does not control.

`frappe.desk.treeview._get_children` (`apps/frappe/frappe/desk/treeview.py`) builds a raw
`frappe.qb` query, filtering only on the parent field, `docstatus < 2` and `disabled`.
There is no permission-query hook and no `has_permission` check. So
`/desk/wallet-category/view/tree` enumerates every user's categories.

### Measurement

Run on `demo.localhost` as a normal (non-Administrator) user:

| Call | Result |
|---|---|
| `frappe.client.get_count` on `Wallet Category` | **107** |
| `treeview.get_children`, empty parent | **180** root nodes |
| Roots not present in the permission-aware list | **150** |

Expanding a leaked node lists its children too — the same raw query runs at every level.

### Severity is bounded

- `frappe.client.get` on a leaked docname returns **403 PermissionError**. This is name
  enumeration, not a record read.
- `Wallet Category` is the app's only `is_tree` doctype. Accounts and transactions have no
  tree view and are unaffected.
- The PWA is unaffected — it goes through `frappe.client.get_list`, which is
  permission-aware.

The names involved are mostly the shipped defaults, which are identical for everyone. The
exposure that matters is a *custom* category, which can be personal.

### Fix

Add `wallet/wallet/doctype/wallet_category/wallet_category_tree.js`:

```js
frappe.treeview_settings["Wallet Category"] = {
	get_tree_nodes: "wallet.wallet.doctype.wallet_category.wallet_category.get_tree_nodes",
};
```

and implement that method with an explicit `owner = frappe.session.user` filter (exempting
`Administrator`, to match `permissions.py`).

### Follow-up

The `permissions.py` docstring tells reviewers to grep for `get_all`. It should also name
`frappe.qb`, and — the part that actually bit here — framework code that queries on your
behalf. A grep of this app's own source would never have found this.

## 2. `Wallet Budget` is referenced but does not exist

**Status:** open

`Wallet Budget` appears in `permissions.py:OWNED_DOCTYPES`, and `hooks.py` therefore
registers both `permission_query_conditions` and `has_permission` for it. No such doctype
exists.

Harmless today — the hooks never fire — but it is a dangling promise. Either build the
doctype or drop the two references.

---

## 3. `requires-python = ">=3.14"` is ahead of the bench

**Status:** open

`pyproject.toml` declares `requires-python = ">=3.14"`. The development bench runs Python
3.12.12. A plain `pip install -e .` would refuse to install.

Either loosen the floor to what the app actually needs, or state why 3.14 is required.

## 4. Test coverage is MCP-only

**Status:** open

29 tests, all in `wallet/tests/test_mcp_tools.py`. They are good tests — isolation gets
the most coverage, deliberately.

But the highest-risk code in the app has none:

| Module | Why it matters | Difficulty |
|---|---|---|
| `statement/parse.py` | date and amount coercion; dd/mm vs mm/dd | **pure functions, trivial to test** |
| `statement/detect.py` | header detection, column mapping, footer markers | **pure functions, trivial to test** |
| `utils/dedup.py` | the three-tier fingerprint | mostly pure; one DB call |
| `api/balance.py` | the balance aggregate and net worth | ~~needs fixtures~~ covered end to end |

The Playwright suite added in #4 now exercises `api/balance.py` end to end — net worth,
the cashflow tiles, per-account balances, and the aggregate's owner isolation — against
seeded fixtures. The three modules above it still have nothing, so this finding stays
open.

`parse.py` and `detect.py` are pure functions over plain lists and strings. They are the
cheapest possible things to cover and they encode the most bank-specific knowledge in the
app — exactly the code that will be edited by someone who has never seen the statement it
was written for.

## 5. The MCP install is not reproducible

**Status:** open, documented in the README

`frappe-mcp` is deliberately not in `pyproject.toml` — it pins `Werkzeug==3.1.3` and
`pydantic~=2.11.7` against Frappe's newer pins, so resolving it would downgrade Werkzeug
and break the bench. It is installed with `--no-deps` instead.

That install lives only in the bench virtualenv. A container rebuild, a fresh `bench init`,
or a Frappe Cloud deploy loses it, and the endpoint fails with
`No module named 'frappe_mcp'`. Nothing in the repo restores it.

The rest of the app is unaffected — nothing else imports `frappe_mcp`.

## 6. `allow_mcp_writes` is site-wide, not per-user

**Status:** open, by design, worth revisiting

`Wallet Settings` is a Single, so `allow_mcp_writes` is one switch for the whole site. On a
multi-user site, one System Manager turning it on opens the MCP write path for every
connected agent — each still confined to its own owner's records, but none of them opted
in.

A per-user opt-in would need a field on `User` or a small per-user settings doctype.

---

## 7. The PWA has no write path

**Status:** open, known gap

The PWA at `/wallet` is read-only. Adding or editing a transaction means falling back to
the desk at `/desk/wallet` — on a phone, which is the one context the desk is worst at.

The API surface for this mostly exists already; what is missing is the UI.
